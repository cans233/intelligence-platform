# 公司技术知识与专利情报系统前端实施分析报告

日期：2026年9月5日

面向读者：项目前端负责人

分析来源：前端PDR V1.0、两人并行开发主控方案 V1.0、实施方案 V1.2（含免费数据源方案）及当前项目工作区。

## 1. 核心结论

两人方案已将B定义为“搜索与产品前端负责人”。按这个分工，B需要交付React页面、OpenSearch索引、查询规划、搜索API和检索质量回归。你目前明确负责前端；应与项目负责人确认本人是否承接完整B范围，或由谁接手B侧的搜索服务工作。报告按完整B范围列出计划，并标明浏览器前端与服务端的边界。

第一轮开发应让同一批样例数据从事实API进入搜索索引，再被页面检索和打开。前端的主要难点是搜索状态管理、事实来源表达、权限边界和审核交互。用户需要知道数据来自哪里、何时核验、为什么命中，以及哪些信息属于系统分析。

实施上沿用已经确定的React、TypeScript和Ant Design，通过契约Mock独立开发页面。B在现有FastAPI模块化单体中实现搜索查询层，A提供事实、权限和索引投递能力。优先复用成熟组件，逐步打通“登录 → 搜索 → 详情 → 来源 → 项目关联 → 审核”。

## 6. 最小技术方案

技术基线已明确为 React + TypeScript + Ant Design。当前没有既有应用可复用，建议采用以下最小组合，具体依赖版本在初始化时确认。

- 构建采用 Vite，路由采用 React Router；组件优先使用 Ant Design 原生的 Layout、Table、Form、Tabs、Drawer、Modal 等。
- 请求统一经过 API Client，处理 `/api/v1`、认证、错误映射、取消请求和 `trace_id`。服务端列表缓存可使用 TanStack Query，避免各页面分别维护刷新、重试和失效逻辑。
- 搜索条件以 URL 为可分享状态来源；表单草稿保留本地状态。先用应用上下文承载必要的登录信息，不预先引入全局状态库。
- Mock 建议使用 MSW，在网络层模拟真实接口，使页面和 API Client 保持同一调用路径。开发环境明确标识Mock，生产构建禁止误启用。
- 公共契约建议以 `contracts/` 内的 OpenAPI 为单一来源，经双方评审后生成 TypeScript 类型；已有团队标准则沿用该标准。
- 按业务 Feature 组织页面。仅提取已经被多个模块消费的组件，例如专利编号、来源、可信状态、高亮、错误态和权限门禁。
- 测试使用 Vitest、React Testing Library 与 Playwright，分别覆盖逻辑、组件交互和端到端路径。

目录围绕 `frontend/src/app`、`api`、`features`、`components`、`mocks` 展开即可，按实际代码创建文件夹。文档第22节是目录建议，当前无需先铺满空目录。

搜索结果和专利列表可共享字段展示、筛选类型及请求能力，不必先做覆盖所有模块的通用页面引擎。专利族和引证先用表格；100条分页先验证性能；Office预览优先消费服务端转换结果。这些选择能够减少前端自研负担。

### 7.2 Mock覆盖

附件第17.2节要求至少准备：中国专利双来源一致、美国专利、多国专利族、来源冲突、至少5项且含长文本的权利要求、缺字段专利。

为支撑真实交互，还建议增加：零结果、多页结果、不同权限、401/403/404、慢响应、请求失败、局部详情失败、未知枚举、审核已被他人处理、监控提交失败。这些是建议补充的测试场景。

Mock负责模拟契约与状态，不需要在浏览器实现搜索排序算法、权限裁决或冲突合并算法。切换真实API后仍需独立验证服务端行为。

## 9. 验收与风险控制

### 每页完成标准

- 正常、加载、空、错误和403状态可验证，404和登录过期按实际页面处理。
- 页面统一调用API Client，字段来源于已确认契约，错误反馈保留必要的 `trace_id`。
- 核心交互至少有正常和失败路径测试，修改操作防止重复提交。
- 1280px可操作，1024px主要按钮不遮挡，复杂表格可横向滚动。
- 键盘可达，图标有可读名称，颜色同时配合状态文本，表单错误定位到字段。
- 刷新详情页不404，权限门禁正确，敏感数据由后端过滤后返回。

### 必须重点验证的链路

| 场景 | 验证内容 |
| --- | --- |
| 搜索状态 | 快速连续搜索、筛选重置分页、URL复制恢复、前进后退、清筛选保留关键词 |
| 搜索安全 | 高亮内容按文本安全渲染，带恶意HTML的片段不会执行 |
| 数据可靠性 | 官方原文、标准化结果、AI结果和人工结论可区分，缺失核验时间不伪造 |
| 长文本与关系 | 权项完整、懒加载、引证跳转、缺失关联记录有明确反馈 |
| 权限 | 无权限数据不进入响应，公开事实可见时内部分析独立受限 |
| 审核 | 必填校验、二次确认、并发失效、网络失败、提交后历史与新状态一致 |
| 索引重建 | 搜索不可用时给出恢复入口，事实详情仍由事实API读取；重建后搜索恢复 |
| 性能 | 在约定数据量及环境下验证首屏建议≤3秒、搜索前端视角P95目标≤2.5秒、100条分页可操作 |

搜索P95是跨前后端的端到端目标，加载提示只能改善等待体验，不能代替性能达标。Golden Set应由搜索负责人维护代表性查询和预期结果，前端参与核对命中解释与交互一致性。

## 10. 建议交付包

按完整B范围，每阶段保留页面与操作清单、API与Mock变化、mapping/query变化、Contract影响、Golden Set及其他测试结果、启动方式和未解决依赖。单独负责React时，由搜索责任人补齐搜索部分，共同验收。

你的第一份开发成果应是“按已确认契约运行的搜索与专利证据流程”。其价值在于提前验证交互、数据表达和协作边界，并为后续项目关联、监控和审核功能建立可复用基础。

## 11. 系统数据怎样到达页面

系统采用FastAPI模块化单体。浏览器经Nginx访问业务API；PostgreSQL保存事实、权限与审计，OpenSearch保存检索副本，S3兼容存储保存文件。Celery与RabbitMQ处理采集、解析和索引任务，Redis承载缓存或短期状态。

外部专利的主要链路是：来源发现 → 原始记录保存 → 标准化和校验 → 解析或可选增强 → 索引投递 → 可检索。A负责数据进入事实库和任务执行；B负责索引设计、查询执行及结果呈现。搜索页读搜索API，详情页读事实API。索引更新可能晚于审核提交，页面需要区分“事实已更新”和“搜索同步中”，具体状态由接口提供。

公司文件走另一条链路：上传 → 文件版本 → 解析 → 索引 → 项目或技术关联。版本切换时要同时切换预览和解析结果，避免展示新版本名称却加载旧文本。解析失败时，原始文件及其受控下载仍应可用。

### 对页面模型最重要的几个区别

| 概念 | 页面与接口需要遵守的含义 |
| --- | --- |
| PatentFamily | 跨国家或地区的同族集合；族内成员仍有独立文本和状态 |
| PatentApplication | 一件申请，可以对应多个公开或授权文本 |
| PatentPublication | 建议作为专利详情路由和全文展示的身份单位；需与A确认`/patents/{id}`的id含义 |
| SourceRecord | 原始来源证据；字段来源需要能定位到具体记录 |
| Search Profile | 可保存、可版本化、可调度的检索策略 |
| Discovery | 某记录如何被发现，关联策略版本、查询和时间 |
| Patent Match | 专利与项目或技术的相关性判断，包含人工反馈 |
| Job | 某次异步执行的状态和尝试记录，不等同于专利的业务状态 |

“为什么当前查询命中”与“为什么当初进入系统”是两个问题。前者是标题、权利要求等命中位置；后者是历史发现路径。结果卡片不能根据当前关键词临时拼出历史发现路径。

Search Profile修改后应产生新版本和生效时间，历史运行仍关联原版本。文档要求可复现检索条件，但未定义历史索引快照；目前不能承诺重新运行就得到完全相同的历史结果。

## 12. 四项契约如何落地

主控方案第7节已经给出了契约基线。当前缺的是仓库中的机器可校验定义和双方确认记录。

| 契约 | 已明确内容 | 开发前还需落实 |
| --- | --- | --- |
| 数据命名 | `publication_number`、`application_number`、`family_id`、`filing_date`、`publication_date`、`priority_date`、`source_code`、`raw_data`、`fetched_at` | 类型、可空、实体id含义、单条来源与`source_codes`集合的区别 |
| API响应 | 成功`code: 0`；失败示例是`PATENT_NOT_FOUND`字符串；统一分页与`trace_id` | TypeScript不能把所有`code`声明为number；稳定错误枚举、HTTP映射和端点Schema |
| 事件Envelope | `event/version/job_id/trace_id/entity_id/source_code/occurred_at/payload` | entity具体层级、payload Schema、重复或乱序处理、索引投递应答 |
| Index Document | 统一文本、编号、日期、分类、来源、`visibility_scope`等字段 | 必填和空值、字段完整性、权限范围、删除与撤权同步、版本与重建方式 |

冻结事件包括 `patent.discovered`、`patent.raw_saved`、`patent.normalized`、`patent.validated`、`patent.parsed`、`patent.enriched`、`patent.index_requested`、`patent.indexed`、`patent.review_required`。这些是内部服务事件，浏览器通过API读取状态；页面无须直接消费消息队列。

发现的索引协议缺口：第6.2节最低字段包含 `technical_problem/technical_solution/technical_effect`，第7.4节JSON样例未包含它们；样例也没有完整的字段来源、核验时间、冲突和发现路径。需要约定搜索响应由索引提供哪些信息、由事实层批量补充哪些信息。避免结果列表逐条发请求形成N+1访问。

`visibility_scope: public`只能表达样例的可见性，不能独立表达部门、项目和文档级权限。A需要给出权限模型和撤权机制，B把过滤应用到命中、总数、聚合、建议词和高亮片段。管理员在实施方案第10节中不默认拥有全部业务内容权限，也必须覆盖这一测试。

## 13. B侧搜索工作拆解

先实现 `patent_v1`，随公司知识接入再实现 `project_v1`、`document_v1`、`technology_v1`。编号、国家和规范化实体用于精确匹配，正文用于全文查询，日期用于范围条件；中文分词、中英术语和IPC上位分类规则需要用样例验证后确定。

主控方案给出的初始权重是标题5.0、关键词或技术特征4.0、权利要求3.0、摘要2.0、说明书1.0，精确编号最高。它们是起始配置，不是质量结论。精确编号匹配应先定义规范化和歧义规则；申请号可能对应多个公开文本，结果不能任意只保留一个。

Query Planner的最小职责是校验输入、识别编号或布尔条件、生成查询与过滤、加入权限约束、映射结果和命中原因。检索式语法只实现双方确认的范围，非法表达式返回可理解的错误。多路外部采集、引证扩展和回溯调度由A执行，B提供策略消费约定和展示，不应把在线搜索请求变成同步外部采集。

Golden Set由知识产权人员提供或确认已知相关专利，B编写可重复运行的查询与评测。主控方案举例每主题100件，不应将该示例直接变成已经批准的样本数量。最低指标包括Recall@K、Precision@20、Precision@100、已知专利命中率、P50/P95和无结果查询率；实施方案还提出MRR、排名变化和漏检清单。

第一次回归先记录基线，再约定通过阈值与允许退化范围。小型fixture用于开发测试，不能证明真实检索召回。修改mapping、analyzer、boost或查询规划时保留回归结果；改变索引结构同时提供reindex方案。建议验证新索引后切换别名，具体流程与A的投递服务协商。

## 14. 免费数据源对前端的影响

V1目标是重点技术领域的持续监控和检索。覆盖范围、更新延迟和待核验信息应让用户看得见，搜索无结果不能直接解释为外部世界不存在相关专利。

| 方案中的来源定位 | 前端应表达的内容 |
| --- | --- |
| CNIPA用于中国专利关键事实核验 | 字段级来源、核验时间、暂不可核验状态 |
| EPO OPS用于全球著录、族、分类、引证等 | 已取得字段与尚未取得全文分开显示 |
| USPTO ODP用于美国官方记录 | 来源与账户接入健康状态，由后端返回 |
| Google Patents BigQuery用于候选补漏与统计 | 候选发现来源和事实核验来源分别显示 |
| WIPO PATENTSCOPE在方案中用于人工核验 | 受控原文或核验入口；不设计自动批量采集按钮 |

实施方案记录EPO每周4 GB、BigQuery每月1 TiB免费查询额度，以及EPO到70%时降低非必要全文获取的策略。这些数值和访问条款需接入时由负责人复核。页面读取后端返回的预算、用量、周期和告警，不把数值硬编码为永久规则。降低抓取频率、预算限制和重试策略在服务端执行，前端展示原因与影响。

建议监控中心展示本次扫描窗口、最近完整扫描、回溯状态和策略版本；数据中心区分限流、认证失败、网络异常、解析失败与额度限制。部分来源暂不可用时保留已有结果，并显示覆盖或新鲜度提示。新增字段先进入Contract Change。

## 16. 两人怎样集成

双方先以同一批fixture为基础：A用它导入事实库、生成Index Document，B用它测试索引、搜索API与页面。Mock响应、事实记录和索引中的id要可对应，否则两个模块各自演示成功仍可能无法集成。

主控方案要求共享契约变更记录 `docs/contract-changes/CC-XXXX.md`，写明原因、旧值、新值、影响、迁移方式和兼容窗口。公共DTO、`backend/main.py`、根Compose或共享环境变量的变更标记集成影响。方案还建议阶段集成、避免超过两个工作日不同步；具体Git操作仍按实际授权执行。

每次集成由A准备空库迁移、Compose、账号和fixture；B验证索引创建、查询和浏览器操作。共同检查：登录 → fixture入库及索引 → 搜索 → 详情 → 来源 → 项目关联 → 冲突审核。再验证重复索引、索引失败重试、撤权、直接API访问受限资源、重建后的搜索恢复。

B交付前端静态构建产物、环境变量需求和深链接约束，A落实Nginx与Compose。应用路由刷新回退与 `/api/v1` 代理需要分别配置；`/api/health`、`/api/ready`是主控方案列出的基础设施端点，不应机械套用业务API前缀。

备份恢复由A主责，B配合检查恢复后的查询、详情、来源和权限。索引清空后能恢复，且事实与原始文件仍完整，才算验证了“可重建索引”。
